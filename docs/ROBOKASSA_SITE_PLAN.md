## 1. Контекст

Writer Tool — SaaS для авторов: структура книги, редактор, персонажи, миры,
таймлайн, экспорт и совместная работа. Сейчас frontend — полностью закрытое
SPA: маршрут `/` только редиректит на `/projects` или `/login`, публичного
лендинга, футера, юридических страниц и SEO-разметки нет.

Планируется принимать оплату через Robokassa. До модерации сайт должен
выглядеть как работающий публичный ресурс: с описанием услуги, реальными
ценами, офертой, политикой ПДн, контактами и реквизитами продавца. Сейчас
проверяющий, открыв `https://tool.melzix.net`, попадёт на редирект входа и не
увидит ни товара, ни документов — это причина отказа.

Задача этого этапа — подготовить сайт, а не подключить платежи. Интеграция
Robokassa (подпись, Result URL, Success/Fail, чеки, подписка, checkout) —
следующий отдельный этап. Здесь создаём публичные страницы, юридические
документы, согласие и границы, после чего можно будет добавить оплату и
отправлять магазин на модерацию.

Дополнительно из документации и практики:

- Для самозанятого в подвале указывается **«Самозанятый ФИО (полностью), ИНН»**;

- Оферта может содержать сразу все условия: услуги, цены, порядок получения,

- Для цифрового сервиса оферта должна описывать, какой доступ предоставляется,

  документом, а не быть встроенным в оферту или политику. Это отдельный

## 3. Принятые решения

1. **Оферта** — рабочая редакция уже подготовлена в
   `docs/block/updated/publicnaia-oferta-dlia-saita-onlain-servis.md`.
   Перед публикацией её нужно проверить у юриста и сверить с генератором
   оферты в Личном кабинете Robokassa; финальный текст утверждает
   пользователь.
2. **Политика ПДн и согласие** — наши черновики по типовым разделам 152-ФЗ;
   обязательна проверка юристом. Мы не заменяем юридическую консультацию.
3. **Согласие на `/login` и `/register`**: два отдельных обязательных
   чекбокса — принятие оферты и пользовательского соглашения, а также
   отдельное согласие на обработку ПДн. Позже на оплате — отдельное
   принятие оферты/согласия. Версии документов передаются на backend и
   фиксируются.
4. **Тарифы**: секция на лендинге + отдельная публичная страница `/pricing`.
5. **Регистрация по email/паролю сохраняется** — `/register` остаётся
   публичной страницей, а Яндекс ID и VK ID добавляются как способы
   регистрации и входа. Для новых OAuth-пользователей включается
   псевдонимизация: не храним реальный email, имя и аватар провайдера,
   только HMAC-идентификатор. Старые email/пароли и аккаунты не удаляются.
   Детали — §3.2 и backend `docs/PSEUDONYMIZATION_PLAN.md`.
6. **Оплата пока выключена**: `PAYMENTS_ENABLED=false`. На сайте показываются
   реальные цены и оферта, но кнопка «Оплатить» появится на этапе интеграции
   Robokassa. До этого CTA ведёт на вход/тарифы.
7. **Данные продавца:** самозанятый Коломойцев Игорь Сергеевич,
   ИНН 410201815392, г. Санкт-Петербург; публичный email —
   `support@tool.melzix.net`; публичный телефон — `+7 999 195-88-80`;
   SMTP-провайдер — Timeweb. Реквизиты должны совпадать с анкетой
   Robokassa.
8. **Цена Pro:** 299 ₽/мес или 2990 ₽/год (RUB, НПД, без НДС). На первом
   этапе — разовая оплата выбранного периода без автопродления.
9. **Компенсация при техническом сбое:** по заявлению пользователя —
   бесплатные дни или месяцы доступа; условия и пороги зафиксированы в
   оферте (§6), механизм начисления — в этапе биллинга.
10. **Оферта:** старый `docs/oferta.docx` — шаблон договора купли-продажи
    товаров, он не используется. Новая редакция — в
    `docs/block/updated/publicnaia-oferta-dlia-saita-onlain-servis.md`:
    доступ к SaaS, 299/2990 ₽, Robokassa, возврат, компенсация, отсутствие
    автопродления, реквизиты самозанятого. Детали — §7.2.
11. **Пользовательское соглашение** — отдельная публичная страница

12. **Cookie-политика** — отдельная публичная страница

### 3.2. Минимизация и псевдонимизация авторизации

С 30.10.2026 принят отдельный курс: не пытаться полностью отказаться от
обработки ПДн, а минимизировать и псевдонимизировать данные.

- Новые OAuth-пользователи (Яндекс ID, VK ID): не храним реальный email,
  имя, аватар и телефон провайдера; храним только HMAC-идентификатор
  `(provider, subject_hash)`.
- Яндекс ID запрашивается с минимальным scope `login:info`; используется
  только `id`.
- VK ID запрашивается с минимальным scope; используется только `user_id`.
- Старые аккаунты, email, пароли и legacy-поля БД пока не удаляются — это
  тестовые данные. Новые OAuth-пользователи получают синтетический
  нерабочий email и пустой password hash, чтобы не менять NOT NULL.
- IP остаётся для rate limiting; для новых OAuth-сессий IP/UA в БД лучше
  не писать.
- Уведомление РКН, оферту, terms, политику ПДн и согласие нужно переписать
  под новую модель; текущий черновик уведомления не отправлять.

Аддитивные миграции `00025_oauth_accounts.sql` и
`00026_oauth_state_purpose.sql` добавлены в backend и применены к
`writer_test`. Backend OAuth, кнопки на `/login` и `/register` и страница
`/auth` реализованы; остались привязка провайдера в настройках, публичный
сайт и юридические тексты. Подробности —
`writer-tool-backend/docs/PSEUDONYMIZATION_PLAN.md`.

### 4.1. Сессия и публичные страницы

Сейчас `rootRoute.beforeLoad` ждёт `bootstrapSession()` на любом маршруте:
лендинг не сможет отрисоваться, если `/auth/refresh` тормозит или недоступен.
Для публичного сайта это неправильно.

Изменения:

- убрать `await bootstrapSession()` из `rootRoute.beforeLoad`;
- `RootComponent` больше не показывает `SplashScreen` на `initializing`, а
  сразу рендерит `<Outlet />`; splash остаётся `defaultPendingComponent` для
  защищённых/auth-маршрутов;
- `loginRoute`, `registerRoute`, `forgotPasswordRoute` сами ждут
  `bootstrapSession()` в `beforeLoad` (как сейчас делает `requireAuth`);
- `shareRoute` ждёт bootstrap, потому что от сессии зависит кнопка принятия
  приглашения;
- `indexRoute` запускает `void bootstrapSession()` в фоне, чтобы шапка
  обновила «Войти» → «Открыть приложение»;
- `App.tsx` `SessionExpiryHandler` не должен уводить на `/login` с публичных
  путей: `/`, `/login`, `/register`, `/auth`, `/pricing`, `/legal/*`,
  `/share/*`, `/verify-email`, `/reset-password`, `/forgot-password`,
  `/confirm-email-change`. На публичной странице 401 просто очищает сессию,
  без toast/редиректа.

Это устраняет зависимость лендинга от API и сохраняет текущие auth-проверки.

### 4.2. Мета-теги

В root добавляется `<HeadContent />` из TanStack Router (React 19 hoists
`title`/`meta`/`link`). Для каждого публичного маршрута задаётся `head`:
title, description, canonical, OG. Для `/login`, `/auth` и защищённых
маршрутов — `robots: noindex,nofollow` (можно централизованно по pathname).

## 6. `/pricing`

- Публичная страница, не дергает `/billing/me`.
- Загружает `GET /billing/plans` (`security: []`); при ошибке — статический
  fallback с теми же Free/Pro, чтобы страница не была пустой.
- Показывает полную таблицу лимитов: проекты, книги, персонажи, события,
  миры, локации, фракции, лор, объём рукописи, хранилище, изображения по
  ссылке.
- Цена Pro берётся из `legal.config.json`: 299 ₽/мес или 2990 ₽/год
  (`priceMonthlyRub`, `priceYearlyRub`), без автопродления на первом этапе.
  Формат: «299 ₽/мес», «2990 ₽/год», «НДС не облагается (НПД)». Пока цены
  не заполнены, `formatProPrice()` возвращает «Цена уточняется», а
  strict-проверка не пропускает production-сборку.
- CTA:
  - `PAYMENTS_ENABLED=false`: «Войти, чтобы подключить Pro» →
    `/login?redirect=/plans`; пояснение, что онлайн-оплата подключается.

### 7.6. Фиксация согласия (backend-зависимость)

Frontend передаёт в legacy `/auth/login` и в
`/auth/oauth/{provider}/start|callback` (Яндекс ID, VK ID) версии
документов:

```json
{
  "offerVersion": "2026-10-30",
  "termsVersion": "2026-10-30",
  "privacyVersion": "2026-10-30",
  "consentVersion": "2026-10-30"
}
```

Backend должен:

- принимать и валидировать версии (текущие/совместимые);
- сохранять факт согласия: `user_id`, тип документа, версия, `accepted_at`,
  IP/User-Agent (если это законно и нужно);
- писать audit-событие;
- по возможности отдавать текущие версии в `/auth/me`, чтобы не показывать
  чекбоксы повторно, если всё уже принято.

Предлагаемая схема (на согласование с backend):

```sql
user_consents (
  id uuid primary key,
  user_id uuid not null references users(id) on delete cascade,
  document_type text not null, -- offer | terms | privacy | personal_data
  version text not null,
  accepted_at timestamptz not null default now(),
  ip inet,
  user_agent text,
  unique (user_id, document_type, version)
)
```

Фиксировать согласие нужно **после успешной аутентификации** (включая 2FA),
а не в момент нажатия кнопки: для email-входа — после `/auth/2fa/verify` или
успешного `/auth/login`, для Яндекса — после успешного callback. Иначе
неподтверждённый вход оставит ложную запись.

Без backend-фиксации чекбокс — только UI и не является доказательством
согласия. Это **launch blocker**; контракт и backend-план нужно обновить до
выпуска. Если backend пока не готов, frontend можно реализовать, но сайт не
считать готовым к модерации.

### 7.8. Компенсация при техническом сбое

Пользователь просит предусмотреть бесплатные дни/месяцы за технический сбой.
Черновик условий для оферты (пороги утвердить с юристом):

- компенсация — бесплатные дни доступа, соразмерные времени недоступности

  недоступности более 72 часов или повторных сбоях в течение оплаченного
  периода;
- компенсация предоставляется путём продления оплаченного периода и не
  заменяет возврат денежных средств, если он положен по закону/оферте;

  лендинга; на `/pricing` — ссылка «Компенсация при сбое».

Механизм начисления бесплатных дней/месяцев относится к этапу биллинга:
нужен административный/биллинговый инструмент, audit-событие и отражение
в истории подписки. В этом этапе фиксируем только публичную политику и
текст оферты.

>
> **Псевдонимизация (30.10.2026):** новые OAuth-пользователи не хранят
> реальный email, имя и аватар. Используются только `provider` и
> HMAC-идентификатор `subject_hash`; Яндекс ID — scope `login:info`,
> VK ID — минимальный scope. Старые email/пароли остаются для legacy-
> аккаунтов. Детали — §3.2 и backend `docs/PSEUDONYMIZATION_PLAN.md`.

   форма входа и кнопка Яндекса остаются только на `/login`.
2. **`/login`**:
   - кнопка «Войти через Яндекс ID» над формой email/пароля, `type="button"`,
     `data-testid="yandex-login"`;

     email-вход, и Яндекс;
   - ссылка «Создать аккаунт» → `/register` сохраняется: регистрация по
     email/паролю остаётся доступной;

3. **`/register`** — публичная страница регистрации по email/паролю;

   чекбоксами согласий; `redirect` сохраняется. Mock-регистрация и тесты
   регистрации сохраняются и обновляются.
4. **`/auth`** — публичный callback OAuth (Яндекс ID или VK ID):
   - читает `code`, `state`, `error`, `error_description`;
   - сразу чистит query через `history.replaceState`;
   - вызывает `POST /auth/oauth/{provider}/callback` с `{ code, state,
     consents }`;
   - `200` → `setSessionFromAuth`, `queryClient.clear()`, переход на
     сохранённый redirect или `/projects`;
   - для OAuth 2FA делегируется провайдеру; собственный экран 2FA не
     показывается;
   - ошибки `invalid_oauth_state`, `oauth_provider_error`,

5. **2FA** — остаётся только для legacy email/пароля; OAuth-входы

6. **SharePage** — оставить «Создать аккаунт» → `/register` для новых
   пользователей и «Войти и принять» для существующих; обе кнопки сохраняют

7. **`safeRedirect` / sessionStorage** — как в плане Yandex; перед уходом
